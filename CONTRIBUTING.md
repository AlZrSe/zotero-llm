## Getting Started

### Prerequisites

- Python 3.12 or higher
- Git
- Zotero account (for Zotero API integration)
- Qdrant instance (local or cloud)
- API keys for at least one supported LLM provider

### Fork and Clone

1. Fork the repository on GitHub
2. Clone your fork locally:
   ```bash
   git clone https://github.com/YOUR_USERNAME/zotero-llm.git
   cd zotero-llm
   ```
3. Add the upstream remote:
   ```bash
   git remote add upstream https://github.com/ORIGINAL_OWNER/zotero-llm.git
   ```

## Development Setup

### Environment Configuration

1. Copy the example environment file:
   ```bash
   cp .env.example .env
   ```

2. Edit `.env` and add your API keys:
   - At least one LLM provider key (OpenAI, Gemini, etc.)
   - Zotero credentials (if using Zotero integration)
   - Qdrant configuration

3. **Important**: Do NOT commit your `.env` file

### Dependencies

Install required packages:
```bash
pip install -r requirements.txt
```

### Docker Setup (Optional)

The project supports Docker deployment:
```bash
docker-compose up -d
```

## Code Style

### Python Guidelines

- Use type hints in all function signatures
- Follow PEP 8 style guidelines
- Use meaningful variable and function names
- Add docstrings to all public functions and classes
- Keep functions focused and small (<50 lines preferred)

```python
        ValueError: If no valid JSON can be extracted
    """
    # Implementation here

```

### Code Organization

Maintain architectural separation:
- `zotero_llm/rag.py` - RAG-specific logic only
- `zotero_llm/agentic_rag.py` - Agentic workflows only
- `zotero_llm/llm.py` - LLM abstraction layer
- `zotero_llm/zotero.py` - Zotero API integration
- `zotero_llm/main.py` - Application entry point and routing

## Pull Request Process

### Before Submitting

1. **Review the AI Usage Policy**
2. Ensure your code doesn't use prohibited Anthropic services
3. Run tests to verify functionality
4. Update documentation if needed
5. Rebase on the latest main branch

### PR Requirements

1. **Descriptive Title**: Clear and concise summary of changes
2. **Description**: Explain what the PR does and why
3. **Testing**: Describe how you tested the changes
4. **Issue Reference**: Link to related issues if applicable

### Code Review

All PRs will be reviewed for:
- ✅ Code quality and correctness
- ✅ Adherence to project architecture
- ✅ **Compliance with AI usage policy (NO Anthropic)**
- ✅ Test coverage
- ✅ Documentation updates

## Testing

### Running Tests

### Writing Tests

- Write tests for new features
- Maintain or improve code coverage
- Follow existing test patterns
- Include both unit and integration tests where appropriate

### Test Categories

- **Unit tests**: Individual function/class testing
- **Integration tests**: Component interaction testing
- **End-to-end tests**: Full workflow validation

## Documentation

### Code Comments

- Comment complex logic explaining "why" not just "what"
- Include examples in docstrings when helpful
- Mark temporary workarounds with TODO comments

### Updating Documentation

If your PR:
- Adds new features → Update README.md
- Changes configuration → Update .env.example and docs
- Modifies API → Update relevant documentation
- Fixes bugs → Update changelog if maintained

## Community Guidelines

### Communication

- Be respectful and inclusive
- Provide constructive feedback
- Accept constructive criticism gracefully
- Focus on technical merit in discussions

### Reporting Issues

- Use GitHub Issues for bug reports and feature requests
- Provide clear reproduction steps
- Include environment details (Python version, OS, etc.)
- Search for duplicates before creating new issues

### Questions?

- Check existing documentation first
- Search closed issues for similar questions
- Open a new issue for clarification if needed
